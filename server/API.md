# PCBA 工作台 API（第一阶段）

FastAPI 同源提供 `/` 与 `/api/*`，默认端口 8001。日期用 `YYYY-MM-DD`，时间用 ISO 8601，数量用十进制字符串。除健康检查、首次建号、账号状态、注册申请和登录外都需 `Authorization: Bearer <token>`。失败返回 `{detail:"..."}`，版本或数量分配冲突返回 HTTP 409。

## 登录与账号

- `GET /api/health` → `{ok:true,database:"ok",backup:{last_local_backup_at,last_local_filename,local_status,local_age_hours,local_stale_after_hours,disk_free_gib,disk_low,last_local_failure_at,mirror_configured,mirror_ok,last_mirror_success_at}}`；数据库不可用返回 503。`local_status` 按实际文件日期为 `fresh|stale|missing`，默认超过 36 小时为过期；`disk_low` 为 `true|false|null`，`null` 表示无法读取空间。数据库 `ok:true` 不代表备份健康。未配置异地备份时 `mirror_ok:null`。
- `POST /api/auth/bootstrap` `{username,display_name,password}`：仅空库一次，且只允许主机本机访问；远程初始化需启动环境变量 `PCBA_SETUP_TOKEN` 与请求头 `X-Setup-Token`。密码至少 10 位。
- `GET /api/auth/status` → `{initialized,registration_open}`；管理员建立后开放注册申请。
- `POST /api/auth/register` `{username,display_name,password}` → `{message,status:"pending"}`。账号为 2–50 位英文字母、数字、点、下划线或短横线，姓名 1–100 字，密码 10–256 位。申请为待审批、不可登录；账号名重复返回 409。
- `POST /api/auth/login` `{username,password}` → `{token,user}`；待审批、被拒绝或停用账号返回 403。同一 IP 在 15 分钟内失败 10 次或同一账号失败 25 次时返回 429 与 `Retry-After: 900`。`GET /api/auth/me` 返回当前用户。`user` 含 `id,username,display_name,role,active,status,permissions`，不返回明文密码、密码哈希或盐。`POST /api/auth/change-password` `{current_password,new_password}` 成功后撤销该账号现有会话，返回 `relogin_required:true`。
- `GET /api/users?status=pending|active|rejected|disabled`：管理员查看全部申请和账号，普通用户只得到启用账号用于分配负责人。管理员 `POST /api/users` `{username,display_name,password,role,permissions?}` 可直接建立已启用账号；角色为 `admin|engineering|business|purchasing|warehouse`。
- 管理员 `POST /api/users/{id}/approve` `{role?,permissions?}` 审批申请；`POST /api/users/{id}/reject` `{reason?}` 拒绝；`PATCH /api/users/{id}` `{display_name?,role?,active?,permissions?}` 修改资料、角色、启停或权限。待审批/已拒绝账号只能用审批接口启用；不能停用或降权自己的管理员账号，也不能停用或降权最后一个启用管理员。角色或权限变更会撤销该用户旧会话。
- 管理员 `POST /api/users/{id}/reset-password` `{password}` 设置新密码并撤销该用户旧会话。系统仅保存 `scrypt` 密码哈希，管理员只能重置，不能查看原密码。权限键为 `orders_edit,production_edit,materials_edit,tasks_manage,imports_manage,audit_view`；普通用户默认开启前四项，导入与审计需管理员授权，管理员拥有全部权限。写接口和导入、审计接口在服务端校验权限。
- 管理员 `GET /api/setup/ownership` → `{users,order_groups,stage_groups}`，列出尚未绑定账号的历史业务姓名与各阶段同名工序。`POST /api/setup/ownership/preview` `{order_bindings:[{legacy_name,user_id}],stage_bindings:[{phase,name,user_id}]}` → `{orders,stages,summary,signature}`，逐条列出拟绑定记录。`POST /api/setup/ownership/apply` 传同一映射、预览 `signature` 和非空 `reason`；版本变动返回 409，成功返回 `{ok:true,summary}` 并逐条审计。已绑定的负责人不会被批量覆盖。

## 订单、外协与交付

### Excel 导出

- `GET /api/exports/project-schedule.xlsx?order_line_id=&phase=`：导出项目排期。`order_line_id` 可选，来自页面的项目键 `line:<id>`；留空导出全部产品行。`phase` 可选，默认为 `all`，也可为 `rd|pp|mp|unclassified`。工作簿含“导出说明、项目清单、生产批次、板件排期、生产节点”五张表。批次共用模式导出批次节点；逐板独立模式导出每块板的厂商、承诺、计划与完工数量，以及逐板节点责任人、计划和实际完成日。正式预测无法确定时，日期保持空白，原因与临时估算分别列出。
- `GET /api/exports/customer-orders.xlsx?q=`：导出客户订单。`q` 可选，匹配项目名、订单号、客户、产品编码或名称；留空导出全部客户订单。工作簿含“导出说明、客户订单、交付批次、生产交付关联”四张表。内部研发项目不包含在内；每个交付批次只统计自己的数量与日期，生产分配另列，不把不同交付批次重复合计。
- 两个接口均要求有效登录 Bearer 令牌，返回 Excel `.xlsx` 附件；无符合条件记录返回 HTTP 404 与可读 `detail`。工作簿内注明筛选范围和导出时间，每张业务表冻结首行并启用筛选。订单号、批次号、产品及板卡编码等标识符以 Excel 文本写入，保留前导零，且不会将以 `=` 开头的用户输入执行为公式；数量为数值，日期为 `YYYY-MM-DD` 日期单元格，缺项保持空白。

- `GET /api/overview` → `{summary:{orders_open,red,yellow,tasks_open,assessable,unassessable,coverage_percent},risks,tasks,orders,assessment,sources}`。`assessment` 对每个未完成项目返回 `{order_id,order_no,project_name,phase,assessable,missing_reasons:[{code,label,entity_type,entity_id}]}`；`coverage_percent` 为可评估项目数占未完成项目数的整数百分比，空列表时为 0。纯研发项目按阶段目标日、预计/实际到板日和节点计划评估，无须伪造客户交付批次；PP/MP 要核对交付数量与两个基准日期、生产分配、厂商承诺、BOM/物料和节点状态。`red/yellow` 只统计已有日期依据的风险项；`unassessable>0` 时，0 红 0 黄不表示交期安全。风险项含 `forecast_status,forecast_date,provisional_date,is_provisional`；`sources` 是 `{orders|bom|inventory|purchases|receipts:最近导入时间}`。
- `GET /api/orders`；`POST /api/orders` `{project_mode?:"customer"|"internal",project_name?,order_no?,customer?,owner_id?,lines:[{line_no,product_code,product_name,quantity,bom_version?}],initial_delivery?}`；`GET /api/orders/{id}`。客户订单须填 `order_no,customer`；内部研发项目可暂不填，由系统生成 `PCBA-PROJ-*` 编号。仅当订单恰有一个产品行时，可传 `initial_delivery:{batch_no?:"D1",quantity?:订单行数量,due_date?,promised_date?,completion_basis?:"shipment",manual_estimate_date?,manual_estimate_reason?,actual_delivery_date?}`，在同一事务中创建交付批次；若填写实际交付日，日期不得晚于今天、初始批次数量须等于订单行数量，并按所选发货/签收完成口径记录整批实际事件。人工预计日必须同时填写估算依据，只作临时预测。订单含 `project_mode,project_name,status:"open"|"complete",total_quantity,completed_quantity`、`owner_name`、`legacy_owner_name`、`owner_binding_status:"bound"|"legacy_unbound"|"missing"`；每条 `line` 含 `completed_quantity`,`production_batches`,`delivery_batches`，交付批次含 `forecast`、`events`。PP/MP 产品行需由交付批次足额覆盖数量，并按该批发货/签收口径足额完成；纯 RD 产品行按调试验收日完成。订单自动更新状态并留痕。
- `POST /api/orders/{id}/lines`；`PATCH /api/orders/{id}`、`PATCH /api/order-lines/{id}` 均提交 `{version,changes,reason?}`。内部研发项目转客户订单时在同一次 PATCH 中传 `changes:{project_mode:"customer",order_no:"正式单号",customer:"客户名"}` 和原因，原研发批次与节点保留；`project_mode`、数量、BOM 版本等关键值更新需原因。订单行 BOM 版本不能与已锁定生产批次冲突。
- 一条产品行可分别建立研发打样 `rd`、PP 试产 `pp`、MP 量产 `mp` 批次；每个阶段独立管理阶段单号、数量、节点、目标日期和实际进度。旧 JSON 导入批次可能为 `unclassified`，须由人员确认；按数量给出的阶段分类只是建议。各阶段的批次数量分别校验，不把研发样板数量从量产数量中扣除。
- `POST /api/production-batches` `{order_line_id,batch_no,quantity,phase:"rd"|"pp"|"mp",phase_order_no?,schedule_start?,schedule_mode?:"workday"|"natural",target_kind?:"internal"|"customer",target_date?,sampling_order_date?,board_eta?,board_received_at?,debug_accepted_at?,vendor?,commit_start?,commit_finish?,bom_version?,bom_items?:[{source_line_no?,material_code,material_name?,quantity_per,loss_rate?}]}`。未指定阶段时默认 `mp`，新建时按所选阶段生成独立节点。`phase_order_no` 是此阶段的订单号，和顶层订单号分别保存；`schedule_start` 是节点草案起点。研发阶段通常跟踪嘉立创打样下单、预计/实际到板和调试验收；PP/MP 才跟踪外协板厂承诺日期。`target_date` 是阶段目标，不自动当作客户交期或板厂承诺。**未配置板卡的单板产品行**若未传 `bom_items`，从已导入的同产品同版本 BOM 目录加载；匹配不到则批次保持未锁定。同一订单行同阶段首个锁定生产批次确立该阶段 BOM 版本；不同阶段的批次可显式选择各自的版本。**已配置板卡的产品行**创建 `bom_scope:"multi"` 批次并复制当前板卡组成及 `board_schedule_mode`，`quantity` 必须是整数件，且不能提交 `bom_items`；后续按板卡逐块锁定。
- `GET /api/production-batches/{id}` 返回批次阶段字段、`order_line`,`product_code`,`product_name`,`order_no`,`bom_items`,`stages`,`materials`,`forecast`,`allocations`,`events`,`conflicts`；`PATCH /api/production-batches/{id}` `{version,changes,reason?}`，`changes` 可含 `phase,phase_order_no,schedule_start,schedule_mode,target_kind,target_date,sampling_order_date,board_eta,board_received_at,debug_accepted_at,quantity,vendor,commit_start,commit_finish`。数量、阶段、阶段单号、目标、到板、厂商及承诺日期等关键值修改需顶层 `reason`。更改起点、日历规则或到板日会顺延尚未手工固定的后续节点。
- `POST /api/production-batches/{id}/bom-lock` `{version,bom_version,items:[{source_line_no?,material_code,material_name?,quantity_per,loss_rate?,unit_price?}]}` 仅用于单板批次；`/bom-lock-from-catalog` 也仅用于单板批次。多板批次须使用下面的逐板锁定接口。同一产品行、同一阶段的单板锁定批次必须使用相同 BOM 版本；不同阶段可各自锁定版本。产品行 `bom_version` 在单板首次锁定时记录主版本，实际生产依据以各阶段批次快照为准。已锁 BOM 明细不随 KIS 目录更新；不能直接覆盖快照。`PATCH /api/bom-items/{id}` `{version,changes:{loss_rate?,unit_price?},reason}` 可维护该批损耗率或单价。
- `unit_price` 为可选的非负人民币单价，最多 8 位小数；BOM 目录导入可映射此列。`GET /api/production-batches/{id}` 增加 `bom_pricing`；`GET /api/bom-catalog/summary?product_code=&bom_version=&quantity=` 返回目录测算。单板或多板共用模式的每行需求量按 `ceil(批量×单位用量×(1+损耗率))` 取整；多板独立模式按下文板卡计划片数计算。各模式都以行需求量乘单价并四舍五入到分。缺价时 `missing_price_count>0`、`total:null`，`priced_subtotal` 只汇总已标价行，不能当成完整总价。
- `PATCH /api/bom-catalog/prices` `{items:[{id,version,unit_price}],quantity?:"1",reason}` 原子批改同一产品同一版本的目录单价；`PATCH /api/bom-items/prices` `{production_batch_id,items:[{id,version,unit_price}],reason}` 原子批改已锁批次快照单价。两者返回更新后的 `items,bom_pricing`，价格变更均须原因并审计。

- `POST /api/delivery-batches` `{order_line_id,batch_no,quantity,due_date?,promised_date?,manual_estimate_date?,manual_estimate_reason?,completion_basis:"shipment"|"receipt",shipping_lead_days?:1,receipt_lead_days?:2}`；`PATCH /api/delivery-batches/{id}` `{version,changes,reason?}`。修改人工预计日、估算依据及关键交期须写顶层 `reason` 留痕；设置人工预计日时还须写 `manual_estimate_reason`，清除日期会同步清除该依据。物流工作日是可调整的人工估算。
- `POST /api/allocations` `{production_batch_id,delivery_batch_id,quantity}`；`DELETE /api/allocations/{id}`。生产和交付批次可多对多，任一侧不得超量。
- `GET /api/phase-templates` 给出三个阶段的初始模板；`GET/PUT /api/products/{product_code}/phase-template?phase=rd|pp|mp` 读取或保存该产品、该阶段的独立模板。PUT 为 `{version,steps:[{name,duration_days,stage_type?:"normal"|"milestone"}],reason?}`，允许 0.5 天粒度；模板只是新批次节点初稿，不代表正式承诺。旧 `GET/PUT /api/products/{product_code}/stage-template` 仅为兼容旧流程，新增排期应使用阶段模板。
- `GET /api/schedule-preview?product_code=...&phase=rd|pp|mp&schedule_start=YYYY-MM-DD&schedule_mode=workday|natural&batch_id?=...&board_eta?=...&board_received_at?=...`：只读推算，复用实际排期的节点耗时与公司节假日规则，返回 `status:"draft",earliest_finish,nodes,source,phase_change_pending`。新批次按产品阶段模板预览；已有批次按本批节点预览，阶段重分类时保留旧节点并提示另行重排。此日期仅是节点草案最早完工，须核对到料和厂商承诺，不是正式客户交期。
- `GET /api/production-batches/{id}/stages`；`POST /api/production-batches/{id}/stages` 可增节点 `{name,owner_id?,owner_name?,stage_type?,duration_days?,actual_material_at?,planned_start?,planned_finish?,actual_start?,actual_finish?,status?,note?}`；`PATCH /api/stages/{id}` `{version,changes,reason?}`，`DELETE /api/stages/{id}` `{reason?}`，`PUT /api/production-batches/{id}/stages/reorder` `{stage_ids:[...],reason?}`。`owner_id` 绑定有效内部账号，`owner_name` 保留旧数据的自由文本姓名；读取节点返回 `owner_display_name,owner_binding_status,is_complete,completed_by,completed_by_name,completed_at`。普通 PATCH 若设为 `done` 或填写实际完成日，也必须先绑定 `owner_id`，并自动记录实际完成日与操作者；撤销完成或修改已完成日期需填写原因。每个节点可指定半天耗时、计划与实际日期、实际到料日和备注；手工调整节点计划后，后续节点按此顺延。删除有实际记录的节点须填原因，重新排序须提交该批全部节点 ID。
- `POST /api/stages/{id}/completion` `{version,completed:true|false,actual_finish?,reason?}` 为节点勾选操作。勾选时需先绑定有效 `owner_id`；未填实际完成日默认当天，不能是未来日或早于实际开始日；任一拥有生产排期编辑权限的内部用户可代录，`completed_by` 记录实际点击人。取消勾选须填原因，实际完成日及本次完成记录会清空，审计保留前后值与原因。并发修改会返回 409，客户端须刷新节点版本后重试。
- `POST /api/production-batches/{id}/generate-stages` `{version,reason}`：从该产品的当前阶段模板重建节点；已有实际工序日期时拒绝重建。普通节点编辑不会自动丢弃原节点。
- `GET /api/vendors/conflicts`；`POST /api/vendors/conflicts/{production_batch_id}/acknowledge` `{reason}`。同厂日期重叠只提示核对，不声称知道真实产能。
- `POST /api/production-batches/{id}/events` `{kind:"material_sent"|"vendor_received"|"finished"|"returned"|"direct_shipped",event_date,quantity?,material_code?,for_material_code?,event_at?,note?}`。发料须填实际料号和数量；替代料另填原 BOM 料号 `for_material_code`，逐料调用。发料从在库预留转为该批已发数量。`finished` 数量累计达本批总量才算完工；省略数量表示剩余未完工量。
- `POST /api/delivery-batches/{id}/events` `{kind:"shipped"|"customer_received",event_date,quantity,note?}`；交付完成按该批选择的发货/签收口径累计。

## 多板项目与 BOM 快照

- 一个客户产品行可以配置多块板，例如 TAV3000 主板和按键板。`GET /api/board-overview` 返回 `{order_lines:{行 ID:摘要},production_batches:{批次 ID:摘要}}`，摘要包含板数、`board_schedule_mode`、确认状态、组成修订号及批次已锁板数。`GET /api/order-lines/{line_id}/boards` 返回 `{order_line,confirmed,boards}`；板卡字段为 `board_ref,board_name,bom_product_code,quantity_per_product,default_bom_version?`。`quantity_per_product` 为 1～10000 的正整数，表示每件成品使用该板的片数。
- `POST /api/order-lines/{line_id}/boards` 提交 `{version,reason,board_ref,board_name,bom_product_code,quantity_per_product,default_bom_version?}` 新增板卡；`PATCH /api/order-line-boards/{board_id}` 提交 `{version,reason,board_ref,board_name,bom_product_code,quantity_per_product,default_bom_version?}` **全部板卡字段**；`DELETE /api/order-line-boards/{board_id}` 请求体 `{version,reason}` 停用板卡。三者均返回更新后的 `{order_line,confirmed,boards}`。每次修改会增加产品行的 `board_set_revision` 并清除组成确认；`POST /api/order-lines/{line_id}/boards/confirm` `{version,reason}` 重新确认完整组成。
- 新批次将当时有效板卡和组成修订号复制为快照。`GET /api/production-batches/{batch_id}/boards` 返回 `{batch,boards}`；每块批次板卡含 `required_quantity=批次成品数×每件用板数`、`bom_locked`,`bom_item_count`,`missing_price_count`；独立模式另含 `planned_quantity,completed_quantity,stage_progress,forecast,conflicts,conflict_acknowledged`。项目组成更改只影响后续新批次，旧批次保留原快照。已有批次只有在**无任何 BOM 明细/已锁板卡且无实际工序或事件进度**时，才可在项目组成已确认后调用 `POST /api/production-batches/{batch_id}/boards/activate` `{version,reason}` 显式启用新板卡计划。历史单板批次不会自动转换，已锁快照不会被覆盖。
- `POST /api/production-batches/{batch_id}/boards/{board_id}/lock-from-catalog` `{batch_version,version,bom_version,reason}` 为**批次板卡 ID** `board_id` 锁定指定母件编码和版本的目录快照，返回 `{batch,boards,bom_item_count}`。每板可用不同 BOM 版本；已锁板卡不能原地换版。`GET /api/production-batches/{batch_id}` 增加 `bom_scope,boards,bom_items,bom_pricing`；每条多板 BOM 明细含 `batch_board_id,board_ref,board_name,catalog_source_line_no`，系统行号为 `B{批次板卡 ID}:{目录行号}`。全部板卡都锁定时批次 `bom_locked=1`。
- 锁入批次时，子件 `quantity_per` 保存“单板目录单位用量 × 每件成品用板数”，并另存 `catalog_quantity_per`。共用模式每条 BOM 行的需求量为 `ceil(批次成品数量 × quantity_per × (1+损耗率))`；独立模式为 `ceil(该板 planned_quantity × catalog_quantity_per × (1+损耗率))`，允许计划片数高于最低成品需求以备损。相同 `material_code` 的需求合并为父批次的一项预留和缺口，`bom_lines` 保留板卡与目录行来源；采购 ETA 和齐套状态也按父批次合并物料管理，板级预测以整批齐套状态为保守门槛。金额按同一行需求量乘单价、四舍五入到分再合计；任何板未锁定或明细缺价时 `bom_pricing.total=null`，已标价部分仅见 `priced_subtotal`。任一板未锁时物料 `status:"bom_unlocked"`、正式预测 `status:"unknown"`。客户交付批次、生产分配与订单完成量都按**成品件数**统计，不乘每件用板数。
- `GET /api/bom-linkages`、`GET /api/order-lines/{line_id}/bom-linkage` 对已配置板卡的产品行返回 `status:"multi_board"`、`board_count`、`board_set_confirmed`；单板关联写接口 `POST /api/order-lines/{line_id}/bom-linkage` 对多板项目返回 409。
- `PATCH /api/order-lines/{line_id}/board-schedule-mode` `{version,mode:"shared"|"independent",reason}` 为该客户产品设置排期方式，返回 `{order_line,mode,existing_batches_unchanged:true}`。历史产品行和生产批次默认 `shared`；`shared` 使用父生产批次的统一厂商承诺与节点，`independent` 使用每块板各自的计划量、厂商承诺、工序和实际完工事件。方式变更只作用于新批次；无任何 BOM 明细/已锁板卡及实际进度的旧批次，可在板卡组成确认后用上述 `/boards/activate` 显式更新。原父批节点的已完成状态不会自动复制到新板节点。
- 独立模式 `GET /api/batch-boards/{board_id}` 返回 `{board,stages,forecast}`。`PATCH /api/batch-boards/{board_id}` `{version,changes:{planned_quantity?,vendor?,commit_start?,commit_finish?},reason}` 修改本板计划片数、外协厂及承诺日期；`planned_quantity` 为正整数片，默认 `required_quantity`，可增加备损，不能低于已登记的实际完工片数。低于交付所需 `required_quantity` 时整批正式预测为 `unknown`。修改开工日会按本板模板重排未手工固定的节点计划。
- 独立模式同厂板卡与其他板卡或共用批次档期重叠时，板摘要的 `conflicts` 显示冲突，未确认会生成核对待办。`POST /api/batch-boards/{board_id}/conflicts/acknowledge` `{version,reason}` 记录该板厂商可以并行生产的依据，返回 `{board,stages,forecast}`；若相冲突计划之后更改，`conflict_acknowledged` 会失效并再次提示确认。
- 独立模式 `POST /api/batch-boards/{board_id}/stages` `{name,duration_days?,owner_id?,stage_type?,note?,reason}` 新增本板节点；`PATCH /api/board-stages/{stage_id}` `{version,changes:{name?,owner_id?,duration_days?,stage_type?,planned_start?,planned_finish?,actual_start?,note?},reason}` 修改。`POST /api/board-stages/{stage_id}/completion` `{version,completed:true|false,actual_finish?,reason?}` 勾选或撤销完成；先绑定有效责任人账号，实际完工日不可晚于今天，撤销或修改已完成日期需原因。独立板节点按板卡母件编码、批次阶段的产品模板生成，和父批共用/历史节点分开保存。
- 独立模式 `POST /api/batch-boards/{board_id}/completion` `{version,quantity,event_date,reason}` 登记本板实际完工片数；须先锁该板 BOM、数量为正整数片，累计不得超过 `planned_quantity`，实际日期不得晚于今天。每板达到 `required_quantity` 才算满足该批成品所需片数；超出部分只是该板备损量，不增加客户交付件数。
- 板卡与父生产批次 `forecast` 均含 `status,formal_date,provisional_date,reason,material_ready_date`；独立模式父批还含 `board_forecasts`。各板 BOM、计划片数、厂商开工/完工日期、物料和节点进度分别校验；任一板为 `unknown` 时父批正式日期也为 `unknown`，`reason` 标明板名及缺项，仅可能显示有依据的临时日期。各板均可预测时父批取**最晚的板卡正式完工日**；各板实际足额完工时状态为 `complete`，日期取最晚实际足额完工日。PP/MP 交付批次仍按物流工作日从父批日期推算，并分别对客户要求日及业务承诺日提示风险。逐板 RD 也要各板 BOM、计划片数、打样厂及承诺日期和物料齐套，才有板级预测；首页将其作为样机目标的计划/临时参考，绝不称为正式客户交期。纯研发项目结案同时要求 `debug_accepted_at` 与全部必要板实际完工片数足额，单填验收日不结案。

## 物料、采购与库存

- `GET /api/materials` 汇总全部生产批次；`GET /api/production-batches/{id}/materials` → `{items:[{material_code,required,reserved,shortage,eta,eta_is_estimate,ready_date,missing_eta,bom_lines,direct_reservation_quantity,direct_reservation_version,issued_quantity,substitute_reservations}],ready_date,status}`，`status` 可为 `ready|forecast|estimated|unknown|bom_unlocked`。当前齐套只计有效合格预留及已发料；预计齐套参考明确、尚未过期且分配到本批的采购 ETA，并标明是否仅为估算。物料精度未知时，每条 BOM 行的十进制需求向上取整到整数件，再按物料编码合计，避免低估缺口。
- `POST /api/inventory/snapshots` `{as_of,basis:"on_hand"|"available",items:[{material_code,quantity}],source_name?}`；`GET /api/inventory` 含 `snapshot_as_of,basis,snapshot_quantity,usable_snapshot_quantity,confirmation_required,capacity,qualified_after_snapshot,issued_after_snapshot,reserved,free,same_day_issue_unresolved`。`snapshot_quantity` 保留源文件原值；最新快照为 `on_hand` 时，`confirmation_required=true`，该快照基数不计入 `usable_snapshot_quantity` 或可预留量。仓库核对冻结、已占用及待检等数量后，使用同一接口提交新的 `basis:"available"` 快照，保留原快照和创建审计；该快照才计入可用库存。快照后的独立 IQC 合格入库仍按原规则计入容量。只有日期的 `as_of` 按台北时间当日结束处理；精确时点快照遇同日但发料时刻不明会标记待核对并阻止进一步预留。
- `PUT /api/reservations` `{production_batch_id,material_code,for_material_code?,quantity,version?}`。`quantity` 是当前**在库预留目标量**，不含已发料；修改已有预留须 `version`。替代料实际料号放 `material_code`，原 BOM 料号放 `for_material_code`。最新快照为 `available` 时，同料所有批次的在库预留不超过其快照基数加之后的 IQC 合格量、扣除之后发料量；最新快照为 `on_hand` 时，该基数不参与预留或齐套，库存不足时返回 409 并提示仓库提交可用量快照。此内部承诺不回写 KIS 锁库。
- `POST /api/receipts` `{material_code,quantity,received_at,source_ref?,source_line_no?,purchase_id?,production_batch_id?}`；`GET /api/receipts`；`PATCH /api/receipts/{id}/iqc` `{version,status:"pass"|"fail",accepted_quantity?,reason?}`。不合格会重算可用量和缺口并生成采购待办。
- `POST /api/purchases` `{material_code,quantity,eta?,eta_is_estimate?:true,reference?,source_line_no?,production_batch_id?}`；`GET /api/purchases` 每行含 `eta_is_estimate`（0/1）与 `eta_source`（`manual|KIS`）；`PATCH /api/purchases/{id}` `{version,changes:{eta?,eta_is_estimate?,quantity?,reference?},reason?}`。手工新增默认估算；改为已确认 ETA 必须有日期与变更原因。KIS 导入 ETA 标为来源 KIS、待人工确认。未指定生产批次的采购行可用 `POST /api/purchase-allocations` `{purchase_id,production_batch_id,quantity}` 分配；合计不可超过采购量。
- `POST /api/substitutes` `{production_batch_id,original_material_code,substitute_material_code,quantity,reason}`；`GET /api/substitutes`；`POST /api/substitutes/{id}/approve` `{version,approve,reason?}`。只有工程账号可审批；批准后仍须仓库预留合格替代料，才计入齐套。

## 预测、待办和管理

生产批次与交付批次的 `forecast` 均含 `status:"complete"|"forecast"|"unknown",formal_date,provisional_date,reason`。共用排期的研发 `rd` 阶段节点日期是打样初稿，正式预测保持 `unknown`；录入 `debug_accepted_at` 后该研发批次记为完成。独立逐板批次使用上文逐板预测规则。纯研发产品行不强制建立客户交付批次，所有研发批次调试验收后订单可完成。PP/MP 缺 ETA、未锁定 BOM 或厂商日期时正式状态为 `unknown`；仅人工估算 ETA 能覆盖缺口时，也保持 `unknown`，单独给临时估算日期并生成采购确认待办。物料晚到、模板计划晚于承诺、工序实际延期，或计划日已过而节点仍未完成时，同样清空正式日期，按超期工作日给出保守的 `provisional_date` 并要求厂商复核；逾期参与日期顺延时的生产批次预测还返回 `overdue_stage_count`。交付风险分别比较客户要求日与业务承诺日；预测延后或已逾期显示红色，提前 5 个公司工作日显示黄色。

交付批次的 `manual_estimate_date` 独立保存；有正式预测或实际完成时不覆盖正式日期。正式预测未知时，`forecast.provisional_date` 取人工预计日与可计算的临时估算日中较晚者，风险标记 `is_provisional:true`。因此该日期不能当作厂商正式承诺。

- `GET /api/tasks?status=open|done`；`PATCH /api/tasks/{id}` `{version,changes:{assignee_id?|status?|note?},reason?}`。业务问题优先给订单负责人，采购/仓库问题按角色默认；转派留痕，只有当前责任人或管理员可确认完成。
- 订单行未排入交付批次的数量大于零时生成 `missing_delivery_batch` 待办；已有交付批次但未足额关联生产批次时另生成 `delivery_unallocated`，标题显示该交付批次尚缺多少数量。交付批次缺客户要求日或业务承诺日时逐项生成 `missing_delivery_date`，已完成的历史批次也会提示。每个生产批次只为当前顺序最前面的逾期未完成节点生成一条 `stage_overdue`，标题汇总其他已逾期节点，优先指派节点有效账号；未经核实的 `on_hand` 造成物料缺口时生成仓库 `stock_confirmation`。条件补齐后自动消除，待办仍需责任人确认。旧待办若尚无责任人，条件同步时会按有效项目/节点负责人或角色默认账号补派并记录 `auto_assign` 审计；先前由系统回退派给管理员的未完成待办，在绑定真实负责人后自动转派并记录 `auto_reassign`。人工转派保持原责任人。
- `GET /api/audit?entity_type=&entity_id=&limit=`：前后值、操作人、时间和原因。
- `GET /api/holidays`；管理员 `PUT /api/holidays/{date}` `{is_workday,description}`。默认周一至周五。
- 管理员 `GET /api/backups`、`POST /api/backups`、`POST /api/backups/{filename}/restore`。恢复前生成安全备份；恢复后须重新登录。每日与导入前自动备份，保留最近 30 份。可设置 `server/.env` 的 `PCBA_BACKUP_MIRROR_DIR` 将每次本机备份复制到第二磁盘或共享目录并校验完整性；目标不可用不会阻止本机备份，故障通过健康检查与日志可见。

## KIS 小批量导入

- `POST /api/imports/inspect` multipart `file`，可选 `header_row,kind`：返回工作表、表头、行数。支持 CSV、XLSX 和含文字表格的 PDF；扫描 PDF 会返回 `errors:[{code:"invalid",message:"…请使用 DeepSeek 智能解析"}]`，这个接口不会自动进行 OCR 或发起网络请求。传 `kind=orders` 时，对已核对版式的 `项目/物料编号/物料描述/数量/交货日期/备注` 返回 `suggested_column_map`，仅供界面预填，仍须人工确认；页眉订单号不自动猜测。传 `kind=bom` 且识别到 `级次` 列中的明确母件与子件、以及 `物料代码` 列时，顶层和对应工作表会返回 `suggested_bom_parent_column:"级次"`；这只是界面提示，不自动启用层级导入。PDF 中重复表头的跨页表格会合并。未解析出的非空页会阻止整份文件应用，避免漏单。
- `GET /api/imports/ai-status`：登录后返回 `{configured:boolean,model:"deepseek-flash"}`，不返回密钥。`POST /api/imports/ai-extract` multipart `file,kind`：须有导入权限，且文件是 PDF。网页选中 PDF 后自动请求此接口；主机将最多 8 页的 PDF 页面渲染成 JPEG 图片并发送给 DeepSeek，原 PDF 文件不会直接发送。响应沿用检查接口的 `sheets:[{name:"CSV",columns,row_count,ai:true}]`、`columns`、`row_count`、`suggested_column_map`、`errors:[]`，并增加 `ai:true`、`ai_extraction_id`、`suggested_fixed_fields`、`warnings`、`cached`、`page_count`。`suggested_fixed_fields` 只是页眉候选值，须人工核对后再作为预览的 `fixed_fields` 提交。相同用户、类型、原文件及模型再次解析会返回缓存，不重复调用 API。
- `POST /api/imports/preview` multipart `file,kind,column_map`，可选 `sheet_name,header_row,key_fields,fixed_fields,snapshot_as_of,snapshot_basis,ai_extraction_id,bom_parent_column`。`kind` 为 `orders|bom|inventory|purchases|receipts`；`column_map` 是 JSON 对象，如 `{"order_no":"销售订单号"}`；`key_fields` 是可选 JSON 字段名数组。`fixed_fields` 是可选 JSON 对象，如 `{"order_no":"SO-123","customer":"甲方"}`，用于把 PDF 页眉中只写一次的值手工补到每条明细；只接受当前导入类型字段，经相同的日期、数量和价格验证。若文件已有该字段映射列，逐行文件值优先，空单元格也不会由固定值补填。使用 `ai_extraction_id` 时仍须上传同一原始 PDF，预览核对用户、类型与 SHA-256 后读取已保存候选 CSV，不再调用 DeepSeek；响应追加 `ai_review` 警告及 `summary.ai=true`。库存缺导出时点或口径时须人工给快照日期与口径。返回 `{preview_id,rows:[{row_index,row_number,key,values,action,changes,valid}],changes,errors,warnings,summary}`。
- `POST /api/imports/apply` JSON `{preview_id,selections:[{row_index,fields?}],reason?}`。新增行应用整行，已有行只应用所选差异字段；数量、交期、ETA、损耗更新需原因。文件级错误不允许应用；行级错误只阻止该行。预览后数据被改动返回 409。响应 `{id,kind,rows_applied,pre_import_backup}`。
- `GET /api/imports`；`GET /api/bom-catalog?product_code=&bom_version=`。源文件、操作者、列映射、页眉固定值、字段选择和导入批次保留；应用前会用相同固定值重新预览，检查并发差异。收到 KIS 脱敏样表前，真实列名与唯一键仍须现场核对。

BOM XLSX 若以 `母件`、`1级子件` 等级次表示多个产品，操作者须在界面明确选择层级列，预览表单才传 `bom_parent_column=级次`。同时将 `material_code` 映射到 `物料代码`、`quantity_per` 映射到 `数量`，按需将 `material_name` 映射到 `物料名称`、`unit_price` 映射到 `参考材料单价`；没有 BOM 版本列时填 `fixed_fields={"bom_version":"实际版本"}`。启用该模式后不能映射或固定 `product_code`、`source_line_no`：产品编码取最近一条明确母件行的物料代码，行号取原 XLSX 物理行号，唯一键固定为 `(product_code,bom_version,source_line_no)`。母件行及无物料编码、无用量的说明/汇总行带提示跳过；级次含糊、子件没有可归属母件的行标为无效。同版本重导入如发生物料与行号错位或与旧平面 BOM 重复，该行标为无效。重新排序或插入 Excel 行会改变匹配键，须逐项核对差异；BOM 改版应填新版本。界面目前按人民币显示价格；若源表未标币种，须先核实。缺价可在 BOM 计价面板补录并按生产数量测算总价。

AI PDF 的 `summary.ai=true` 表示候选识别结果。网页将本地原始 PDF 与全部字段逐行并排显示，提供新增、差异、错误筛选和候选行数核对；AI 新增行默认**不勾选**，已有行的差异字段也默认不勾选。操作者需对照原件，逐项选择要应用的行或字段；筛选及界面刷新会保留已选内容。普通 CSV/XLSX 的新增行仍默认勾选。原件对照使用当前浏览器的临时 PDF URL，换文件、离开导入页或应用成功后释放；无法内嵌显示时可在新窗口查看。BOM 价格覆盖数量和销售订单有效行数量合计在预览中辅助核对，正式 BOM 总价仍须按生产数量与损耗测算。

在主机的 `server/.env` 中设置 `DEEPSEEK_API_KEY=...`（模板见 `server/.env.example`），或设置同名进程环境变量；不要把密钥放入网页或仓库。选中 PDF 后，网页会自动调用 DeepSeek；图片可能包含客户及单据信息。单文件上限 20 MB，AI 最多 8 页、每页最多 1000 万渲染像素且长边不超过 8192 像素、JPEG 单页最多 4 MB、总量最多 16 MB；候选表格最多 2000 行、60 列。这些限制低于 [DeepSeek Vision 官方上限](https://api-docs.deepseek.com/guides/vision/)。主机只短时渲染图片，不加载常驻 OCR 模型。扫描模糊、跨页错列、看不清的字符可能导致候选值错误或缺失；映射、逐行预览和选行应用仍为必经步骤。AI 候选 CSV、原 PDF、用户、模型、固定值与应用选择分别持久保存以供追溯，应用前从保存候选重算差异，不会再次付费解析。未应用候选保留 7 天，超过 50 份时清理已超过 24 小时的最旧项；已应用候选保留供审计。

已提供的销售订单 PDF 样例是原生文字表格，`交货日期/备注` 在无备注时可为 `YYYY-MM-DD /`，导入日期规范化会识别空斜杠；若斜杠后有实际备注，则保持行级错误，避免悄悄丢弃备注。样例页眉订单编号未可靠地保留在文字表格中，应由操作者核对后填入 `fixed_fields.order_no`。样例明细后的单格说明行会保留为无效行供核对，有效明细可逐项选择导入。

## 旧 HTML 排期 JSON 迁移

- `POST /api/legacy/preview` multipart `file`：读取旧页“导出配置(JSON)”文件，返回 `preview_id`、逐产品 `action:create|duplicate|invalid`、原节点、缺项和错误。只预览，不创建订单。
- `POST /api/legacy/apply` JSON `{preview_id,selections:[{index}]}`：只导入选中的有效产品；重复旧产品 ID 不覆盖已导入订单。响应含 `created:[{order_id,order_no,order_line_id?,production_batch_id?,legacy_record_id,pending_fields}]`、`skipped` 和导入前备份名。
- `GET /api/legacy/records?order_id=`：返回旧产品和节点原始 JSON、关联订单、当前 `missing_fields` 与 `status:pending|complete`。待补字段随当前订单、BOM、外协和交付记录重算；首页生成 `legacy_pending` 待办，字段补齐后条件自动消除。

每个导入产品生成一个临时订单；有有效数量时同时生成产品行和未锁 BOM 的阶段批次，数量为空时只保留订单与旧记录。旧产品名进入产品行；旧负责人姓名会以 `legacy_owner_name` 保留并供界面显示，但在绑定真实工作台账号前仍显示“负责人账号待绑定”，不能当作系统登录用户。旧起始日期、日历规则、每道节点的名称、负责人、以 0.5 天为步长填写的原耗时、旧预计日期、实际到料/完成日期和备注按源文件复原为历史排期；上传文件中每个产品原有的 11 道节点会保持原顺序。系统按旧页面的 12 小时步长重现历史估算，`legacy_schedule` 可在旧记录接口查看。旧预计日期只作历史估算，不能自动变成新流程的正式客户交期或厂商承诺；阶段由数量作初始建议，需人工核对。对以前已导入、仍为未编辑通用节点的记录，启动迁移会恢复原节点；人工改过的节点不会被覆盖。导入前做数据库一致性备份，保留源文件及操作审计。
